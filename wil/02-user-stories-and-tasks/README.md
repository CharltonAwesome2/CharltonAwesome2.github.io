# User Stories and Tasks

## Overview

This section presents user stories and associated development tasks for four professional software development projects.

A user story describes a requirement from the perspective of someone interacting with a system. Tasks break that requirement into smaller development activities.

The stories in these documents were reconstructed retrospectively from the work performed, requirements communicated during development, available development records and personal recollection. They were not originally maintained as formal Agile user stories.

## How to interpret the stories

Each story follows this general format:

> As a [user], I want [functionality] so that [intended benefit].

The associated tasks describe the development activities required to implement the functionality.

### Status definitions

- **Completed:** The described functionality was implemented.
- **Partially completed:** Some of the functionality was implemented, but further work remained.
- **Incomplete:** Development had started or the requirement had been identified, but the functionality was not finished.
- **Not started:** The functionality had not been implemented.
- **Planned:** The functionality was identified as a future requirement but was not implemented.

A completed story does not necessarily mean that the entire project was completed. Some projects were paused or discontinued while other functionality remained outstanding.

## Retrospective approach

The purpose of this section is to demonstrate how the development work can be organised using Agile user stories and tasks.

The original development process did not use a formal user-story management system. These documents therefore represent a retrospective organisation of actual work rather than original planning records.

User roles are representative of the intended system users and do not imply that formal user research or user-story workshops took place.
