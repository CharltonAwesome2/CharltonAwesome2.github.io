# Reflection: User Stories and Tasks

## 1. Understanding Requirements from a User's Perspective

Before preparing this document, I generally approached development by identifying the functionality that needed to be implemented and then working through the technical requirements.

Breaking the work into user stories helped me consider the functionality from the perspective of the people who would interact with each system. Rather than focusing exclusively on what needed to be programmed, I could identify the purpose of each feature and the value it was intended to provide.

For example, implementing search functionality is a technical task. However, the underlying requirement is that a user should be able to find relevant information efficiently. This distinction helped me understand how technical implementation relates to user needs.

## 2. Breaking Work into Smaller Tasks

The development of these projects involved several interconnected areas, including database design, backend development, frontend implementation, integration and testing.

Breaking larger requirements into smaller tasks makes development easier to understand and manage. It also helps identify dependencies between different parts of a system.

I found this particularly relevant when working on functionality that depended on multiple components. A feature might require database changes, backend operations and corresponding frontend functionality before it could be considered complete.

Representing this work as individual tasks makes it easier to identify what needs to be done, what has already been implemented and where further work is required.

## 3. Managing Incomplete Requirements

Not every requirement was completed across the projects. Some functionality was partially implemented, while other work had not started when development stopped or was paused.

Separating completed, partially completed and outstanding work provides a more accurate representation of project progress. It also prevents the assumption that completing one part of a system means that the entire feature or project is finished.

This exercise highlighted the importance of maintaining a clear record of outstanding work. Without one, it becomes more difficult to determine what remains to be implemented, particularly when development is interrupted or priorities change.

## 4. Applying Agile Techniques Retrospectively

I did not originally create formal user stories or break requirements down into tasks using an Agile task-management tool. Requirements were communicated primarily through my supervisor, and I independently translated them into development work.

Preparing these user stories retrospectively has helped me understand how an Agile approach could have improved the organisation of my work.

If I were to approach these projects again, I would document requirements as user stories before implementation, identify the tasks required to complete each story, and maintain their progress in a backlog.

This would provide a clearer connection between stakeholder requirements, development activities and completed functionality.

## 5. Lessons Learned

One of the main lessons from this exercise is that implementing functionality and understanding the underlying requirement are closely related but not identical activities.

A developer needs to understand why a feature is required before deciding how to implement it. Breaking requirements into user stories encourages this consideration and provides a clearer basis for development decisions.

I also recognise the value of documenting progress consistently. Although I was able to reconstruct much of the work using my development history and recollection, maintaining user stories and tasks throughout development would have made progress tracking and future maintenance easier.

## 6. Overall Reflection

Preparing this deliverable has helped me understand how user stories and tasks can be used to organise software development work.

Although I worked independently and did not formally follow an Agile framework, many of the activities I performed can be represented through Agile concepts. This exercise has shown me how a more structured approach to requirements, task breakdown and progress tracking could improve my development process.

Going forward, I intend to make user stories, smaller development tasks and clearer progress records part of my regular development workflow.
